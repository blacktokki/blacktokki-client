# 관계 분석 성능 회귀 테스트

`analysis.test.cjs`, `search-cache.test.cjs`, `search-input.test.cjs`, `search-browser.test.cjs`는 키워드 및 관계 확장 내부의 회귀 테스트입니다. 기존 `test:keywordRelation`과 `test:knowledgeGraph` 명령에서 함께 발견되며, 성능 테스트만 실행하려면 저장소 루트에서 다음 명령을 사용합니다.

```powershell
yarn workspace @blacktokki/notebook test:keywordRelation:performance
```

기본 검사는 메모리에서 생성한 합성 노트 72개로 실행합니다. 테스트 데이터에는 로컬 노트북의 원문·제목·주소·내보낸 연결 구조와 파생 데이터를 사용하지 않습니다. 로컬 노트북을 직접 읽는 실행 경로도 제공하지 않습니다.

파일 API 대기 시간 재현 검사는 별도로 32개 폴더의 파일 640개에 `getFile()` 70ms·`text()` 50ms의 대기를 적용합니다. 파일 조회와 캐시 확인이 5초 이내인지 검사하며, 브라우저와 Node 파일 API의 응답 시간 차이를 빠른 디스크 읽기만으로 가리지 않도록 합니다. 이 대기는 실제 브라우저 실측값이 아닌 회귀 검사 조건입니다.

검색 캐시 검사는 합성 검색 문서 8,191개·384차원 벡터의 약 51MB JSON을 실제 캐시 디코딩·검증과 인덱스·질의 점수 계산 코드로 처리합니다. 저장소 읽기 1,500ms·검색 자료 준비 1,400ms·모델 초기화 2,300ms를 재현하고, 캐시 확인부터 인덱스·모델 준비 및 첫 질의 점수 계산까지 5초 안에 완료되는지 검사합니다. 저장소 읽기와 모델 생성은 각각 한 번이어야 하며, 완료된 문서를 다시 임베딩하면 실패합니다. 대기 시간은 회귀 검사 조건이며 실제 IndexedDB·모델·브라우저를 실측한 값은 아닙니다.

`search-input.test.cjs`는 합성 노트 512개에서 문단 8,192개와 키워드 2,048개를 구성합니다. 실제 원문 기반 항목·관계 구성, 입력 식별, 근거를 보존하는 검색 자료 생성, 인덱스 구성까지 포함하고 약 246MB의 저장 벡터 JSON을 복원합니다. 모듈과 입력을 새로 생성하고 원문 기반 구성을 시작한 시점부터 첫 질의까지 5초를 검사하며, 원문 기반 구성·입력 식별·저장소 읽기·모델 생성은 동시 소비자 사이에서 각각 한 번만 실행해야 합니다. 번역 함수는 실제 훅처럼 소비자마다 다른 참조로 생성합니다. 브라우저 DOM 표면은 합성 HTML 전용 어댑터로 대체하며 저장소 읽기 1,400ms와 모델 초기화 2,300ms만 지연으로 재현합니다.

`search-browser.test.cjs`는 설치된 Windows Chrome 또는 Edge를 별도 임시 프로필로 실행하고 검사 후 정리합니다. 브라우저가 없으면 이 검사만 건너뜁니다. Node 20에서는 내장 WebSocket을 켠 자식 프로세스로 자동 실행하며 추가 라이브러리는 사용하지 않습니다. 메모리에서 생성한 노트 128개의 문단 8,192개와 HTML ID를 실제 에디터의 DOM·Markdown 변환, 근거 구성, 검색 색인 코드로 처리하며, 약 263MB의 JSON 벡터 캐시도 실제 IndexedDB에 저장한 뒤 읽습니다. 저장소·DOM 처리와 겹치는 모델 준비 대기 2,300ms를 재현하고 전체 준비가 5초 이내인지 검사합니다. 원문 구성과 캐시 읽기는 실제 브라우저 코드이며 모델 다운로드·GPU 추론 자체는 실행하지 않습니다. 개인 브라우저 프로필이나 로컬 노트북은 읽지 않습니다.

브라우저 검사는 HTML ID마다 원문 앞부분을 다시 파싱하지 않는지도 확인합니다. HTML ID 16개가 있는 원문에서 구조 분석의 DOM 파싱은 2회 이하여야 하며, 다국어 원문 위치·링크 근거·숨김 메타데이터 제외 결과를 검증합니다. 보통의 텍스트 문단은 HTML→Markdown 재변환을 생략하고, 같은 HTML의 근거 구조와 문단 경로 해석은 한 번만 수행합니다.

상위 `relation-controller.test.cjs`는 설치된 React Query의 실제 캐시와 관찰자로, 첫 조회가 끝난 뒤 일반 노트·템플릿·비공개 분석이 붙어도 파일을 다시 읽지 않는지 검사합니다. 수동 새로고침·저장 후 무효화·조회 유효 시간 만료 시에는 다시 읽고, 원문이 같으면 분석 입력의 참조가 유지되는지도 확인합니다. 검색 통합 검사는 분석 결과 전달이 늦어져도 원문을 재조회하지 않는지 확인합니다.

Web Crypto와 JavaScript 대체 해시 구현을 모두 검증합니다. 각 구현에서 합성 노트의 새 분석과 저장 캐시 복원을 실행합니다. 32Mi 문자 이하 입력은 Web Crypto의 SHA-256을 사용하고, 더 큰 입력이나 Web Crypto가 없는 환경은 메모리를 제한한 대체 구현을 사용합니다. 두 방식의 해시가 같으므로 기존 캐시를 무효화하지 않습니다. 원문 조회를 포함한 캐시 준비와 캐시 확인 자체는 각각 5초, 전체 분석은 각 실행에서 15초로 제한합니다.

- 원문 로딩부터 캐시 사용 가능 여부 확인, 수집 또는 복원, 통계 평가, 캐시 저장, 단계별 요약 및 최종 로그 데이터 생성까지 측정합니다.
- `readinessMs`는 원문 조회를 포함한 캐시 준비 시간, `cacheCheckMs`는 관계 캐시 확인 자체의 시간이며, 둘 중 하나라도 5초를 넘으면 실패합니다.
- 매번 분석 세션 메모리를 비우고 새 파일 핸들을 사용해 완료 결과나 변환 캐시가 성능 문제를 가리지 않도록 합니다.
- 노트를 동시에 조회하는 소비자 3개와 보드 소비자 1개를 실행하고, 각 노트 파일을 한 번만 읽는지 확인합니다.
- 캐시 확인 단계에서 수집·평가를 실행하지 않고, 복원 시 키워드·유형·문맥·관계 후보를 다시 수집하거나 캐시를 다시 저장하지 않는지 확인합니다.
- 결과와 관계별 근거는 객체 필드 순서를 정규화한 해시로 비교합니다. 반복 실행·해시 구현·캐시 복원 사이에 결과가 달라지면 실패합니다.
- 처리 단계, 소요 시간, 파일·캐시 읽기/쓰기 횟수는 `t.diagnostic`으로 출력합니다. CPU 프로파일러나 전역 모듈 로더 교체는 사용하지 않습니다.

추가 라이브러리를 설치하지 않습니다. 실제 저장소 읽기·분석·직렬화·검증 코드를 사용하며, 관계 캐시는 테스트 전용 메모리 어댑터로 격리합니다. 관계 분석 검사는 지식 그래프 구성과 검색 입력 식별을 제외하고, 검색 입력 검사는 이 두 과정을 포함합니다. 브라우저 검사는 실제 IndexedDB와 DOM 처리도 포함하지만 실제 모델 다운로드·GPU 추론과 앱 화면 렌더링은 포함하지 않으므로 사용 중인 노트북의 완료 시간을 보장하지 않습니다.

## 브라우저 실측 로그

- `검색 준비: 처리 시간` 하나에 화면에서 검색 준비로 넘어간 시점부터 입력의 렌더링·준비 대기, 검색 입력 식별, 캐시 읽기·검증, 인덱스·벡터·모델 준비까지 측정합니다.
- 앞서 실행한 관계 캐시 확인의 대기·원문 식별·저장소 조회·전체 시간과 캐시 상태도 같은 요약에 포함하며, 기존 관계 캐시 성능 로그는 따로 출력하지 않습니다. `경과ms`는 검색 준비 구간이고 `관계캐시확인ms`는 앞선 관계 캐시 점검 구간입니다.
- 실제 저장소 읽기, JSON 해석, 저장 형식 검증 시간과 저장 문자 수·벡터 수도 같은 로그에 포함합니다. 저장소 계층에서는 별도 로그를 출력하지 않으며, 공유된 읽기 결과에서도 세부 시간을 전달합니다. `저장소조회재사용`으로 공유 여부를 구분합니다.
- 모델 파일과 저장소 읽기는 노트 원문 로딩 이전부터 병행합니다. 첫 추론은 원문을 받은 뒤 같은 모델로 수행하며, 원문이 도착해도 모델을 해제하거나 다시 불러오지 않습니다. 인덱스 구성도 저장소 읽기와 병행합니다. 검색 준비 완료는 인덱스·벡터·모델이 모두 준비된 뒤에만 표시합니다.
- `검색자료구성`·`검색색인구성`은 인덱스 준비를 나누어 측정합니다. 다른 소비자가 먼저 구성한 자료의 시간도 같은 요약에 전달합니다. `모델파일준비`·`모델첫추론`으로 모델 파일 준비와 첫 추론도 구분합니다. 먼저 시작한 작업의 `시작ms`는 음수로 표시하여 전체 경과보다 오래 걸린 선행 작업을 구분합니다.
- 각 실행이 완료·실패·중단될 때 한 번만 출력합니다. `경과ms`는 전체 시간이며, `5초초과`와 `작업시간`의 시작·경과·상태로 병목을 구분합니다. 병행·포함 관계 때문에 개별 시간의 합과 전체 경과는 다를 수 있습니다. `(대기포함)`은 공유 작업이나 모델의 실행 차례를 기다린 시간도 포함합니다.
- `측정ID`·`분석실행ID`·`시도횟수`로 중단과 재시작을 구분합니다. 로그에는 범위 ID·건수·시간·준비 상태만 기록합니다.

`search/__tests__/diagnostics.test.cjs`는 원문 렌더링 전부터의 시간 보존, 준비 대기와 병행 작업, 완료·실패·중단 시 한 번만 출력하는 동작, 공유된 저장소 읽기의 계측 전달, 동기 JSON 해석 시간의 분리를 검증합니다.
